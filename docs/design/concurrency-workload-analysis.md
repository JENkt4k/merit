# Concurrency workload analysis

**Design review only.** Source: [36-workload catalog](https://github.com/JENkt4k/solution-compass/blob/codex/merit-concurrency-catalog/src/data/merit-concurrency.json), schema v1, branch `codex/merit-concurrency-catalog`, read 2026-11-10. The catalog states desired contracts and metrics, not Merit implementation evidence. All concurrency APIs mentioned here are proposed. Current Merit has owned moves, call-scoped borrows, exact numeric types, capability checks, and C interop; it has no established threading, channels, actor runtime, atomics, send/share constraints, or stored local borrows. See `spec/OWNERSHIP.md`, `LIMITATIONS.md`, and `docs/design/alpha3/BORROW_MODEL_DECISION.md`.

## Cross-cutting interpretation

Memory safety and data-race freedom can be language obligations once concurrency exists. Queue ordering, fairness, progress, cancellation, transaction isolation, durability, and exactly-once effects require explicit library/runtime/protocol contracts. A compiler cannot infer them from `Owned`, a capability token, or a single-writer actor. The catalog's `evidence: []` entries provide no benchmark or correctness measurements. For each workload, establish a sequential oracle or history checker, a declared operation order, fault points, resource accounting, and a bounded test. Compare performance only after safety and semantic invariants pass.
